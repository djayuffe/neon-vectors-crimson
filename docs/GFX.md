# Graphics

PAL low-resolution 320×256, **three bitplanes** (eight colours), driven by a Copper list that
also does the colour work: gradients per raster line, the depth shades of the starfield and the
animated bar under the logo.

## Screen layout

| Rows (y) | Band | Content |
| --- | --- | --- |
| 8–71 | Logo | `UBER` (5× glyphs) over `CRACKING SERVICE` (2×), rules and corner brackets |
| 72–75 | Bar | animated colour bar (the `cop_raster_color` slot) |
| 76–195 | Middle | 3D starfield behind a rotating wireframe |
| 200–215 | Scroller | 16-line scroller strip, with frame lines |
| 222–255 | Floor | animated Copper bars, no bitmap |

Display line = row + 44. The Copper wraps the vertical counter with `WAIT $FFDF,$FFFE` for
rows 212 and up (display lines above 255).

## Bitplanes and colour

The chip block holds four plane-sized buffers: plane 0, **wireframe buffer 0**, **wireframe
buffer 1**, plane 2. The display's plane 1 is whichever wireframe buffer is currently in front.

| Plane 0 | Plane 1 | Plane 2 | Colour index | Used for |
| :-: | :-: | :-: | :-: | --- |
| 1 | | | 1 | logo / scroller text (Copper gradient); mid-distance star in the middle band |
| | 1 | | 2 | wireframe |
| | | 1 | 4 | far star (dim) |
| 1 | | 1 | 5 | near star (bright) |
| any with plane 1 | | | 3, 6, 7 | wireframe colour again, so the wireframe is always in front of stars |

`COLOR01` is changed by the Copper per band, so the same plane-0 bit is gold text in the logo,
blue-white text in the scroller and a grey-blue star in the middle.

## Wavy logo

Every logo row (8–71) has a `WAIT; MOVE COLOR00; MOVE COLOR01; MOVE BPLCON1` entry in the Copper list
(`cop_wave`, 16 bytes per row). `UpdateWave` rewrites the 64 `BPLCON1` values each frame from the
256-entry `wave_tab`, indexed by `(4 · frame + 3 · row) & 255`: a sine of 2–14 pixels of horizontal
scroll (the same nibble for both playfields), about 1.3 waves over the logo and one wave per 64
frames. The tail below the logo resets `BPLCON1` to 0.

Hardware scroll needs one extra word per line, so the display fetches 21 words (`DDFSTRT` $30
instead of $38), the bitplane pointers point **2 bytes before** each plane, and `BPL1MOD`/`BPL2MOD`
are −2 (21 words fetched, 20 words per line). The extra word at the left edge is hidden by the
display window; with a scroll of *s* its last *s* pixels slide in, which in the logo band are
blank. The chip block carries a spare longword before plane 0 for the first line's extra fetch.

## Logo

Generated by `tools/generate_assets.py` from an embedded 5×7 glyph set: `UBER` at 5× scale and
`CRACKING SERVICE` at 2×, each centred on its ink, with two rules and corner brackets. The
validator requires every ink pixel to stay inside x = 1..318 and y = 1..62. The gold-to-orange
gradient is pure Copper: one `COLOR01` change on every row.

## 3D starfield

64 stars, each with (x, y, z). Every frame `z` falls by 2; at z = 32 the star is sent back to
z = 255 with a new x and y from a 16-bit LCG. Projection is

    screen x = 160 + x · 128 / z      screen y = 136 + y · 128 / z

so near stars race outward faster than far ones. A reciprocal table (`recip_star`) replaces the
division: `screen = (coordinate · recip[z]) >> 8`, one `MULS` instead of `DIVS`. Stars outside the
middle band are skipped.

Depth is shown as brightness using the planes the middle band leaves free: far (z > 150) is
plane 2 alone, mid (z > 80) plane 0 alone, near plane 0 + 2. Each star remembers the byte offset,
bit mask and class it was drawn with, and the next frame erases exactly that — all stars are erased
first, then all are drawn, so two stars sharing a byte cannot erase each other.

Stars are single-buffered, which is safe because they are updated first in the frame and finish
(about 18 000 cycles, worst frame) before the beam reaches the starfield band.

## Wireframe

A cube (half-size 42) and an octahedron (radius 28) rotate in opposite directions, 24 edges in
all, in a 120-line band. They also follow a motion path: the centre sways ±64 pixels with the x
angle and the distance breathes ±18 units with the y angle (`wire_cx`, `wire_zoff`), so the object
swings from side to side and in and out.

Per frame:

1. the blitter clears the hidden buffer's band (D-only blit) while the CPU works;
2. `CalcMatrix` builds two 3×3 rotation matrices from 7-bit sine/cosine, scaled by 128;
3. `TransformVerts` rotates and perspective-projects the 14 vertices,
   `screen = centre + r · 220 / (z + 300)`, again via a reciprocal table;
4. `BlitLine` draws each edge with the blitter in **line mode** (below);
5. next frame `WireSwap` points the Copper at the finished buffer, so the display never shows a
   half-drawn picture.

**Line mode.** The octant bits in `BLTCON1` come from the Hardware Reference Manual's table 6-3
(`octants` in the source), `dmaj`/`dmin` are the larger/smaller of |dx|, |dy|, and

    BLTAPT = 4·dmin − 2·dmaj    BLTAMOD = 4·(dmin − dmaj)    BLTBMOD = 4·dmin
    BLTSIZE = ((dmaj + 1) << 6) | 2    BLTCON0 = (x1 & 15) << 12 | $0BCA

`ONEDOT` is left **clear**: it is for area-fill edges, and with it set shallow lines come out with
gaps. The registers that never change between lines (A/B data, masks, C/D modulo) are set once per
frame. There is no clipping: the object is sized to stay inside its band, and the emulation test
asserts it.

## Copper-bar floor

The 34 floor rows (222–255) are one `WAIT; MOVE COLOR00` entry each (`cop_bars`, 8 bytes per row).
Each frame `UpdateBars` resets them to a purple ramp (`floor_base`) and then paints four bars of
eight rows (magenta, cyan, gold, green; `bar_colors`, bright core and soft edges) over them. Each
bar's centre follows `17 + 13 · sin(frame · (k + 2) + 64 · k)`, so the bars move at different speeds
and later bars are in front. All of these rows are below display line 255, after the Copper's
vertical-counter wrap.

## Scroller

Planar pixels are MSB first, so scrolling left shifts each row as big-endian longwords from the
rightmost to the leftmost with `ROXL`: bit 31 of one longword falls into X and enters the next
longword to its left at bit 0. X must start at zero for each row, and `MOVEQ` does not touch it, so
it is cleared explicitly with `andi #$EF,ccr`. Every second frame the band moves one pixel, then
the next column of the current glyph is written into bit 0 of the last byte of each of the 16 rows
(each of the 8 font rows on two lines). The strip is far down the screen and is shifted before the
beam gets there, so it is single-buffered.

## Copper

The list sets display fetch/window registers, `BPLCON0` (three planes), the six pointer pairs
(`PatchCopper` rewrites the **data** words at offsets 2/6, 10/14 and 18/22 from `cop_bpl1` every
frame, because plane 1 alternates), the static palette, and then the per-row entries described above:
64 wave rows, a mid-band glow, the scroller strip and 34 bar rows (`tools/gen_tables.py copper`
generates them; the wave and bar values are patched at run time).

## Verification

`tools/emu_test.py` renders the Copper list and bitplanes exactly as the chipset would show them
and compares them with independent Python reference models: the logo bitmap, every star position
and depth class, every scroller pixel, the wave and bar rows, and — on **every** frame — the whole displayed wireframe
buffer against the reference projection and a reference Bresenham. The blitter's line mode itself
was confirmed on real (emulated) hardware by running the program in FS-UAE.
